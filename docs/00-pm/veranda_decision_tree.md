# 베란다 자동 분류 의사결정 트리 (v2.2 현행)

> **대상 코드**: `src/lib/verandaAi.ts` `classifyBuildingWalls()`
> **목적**: 벽면 하나가 first / second / concrete 중 무엇이 되는지, 판정 순서 그대로 구조화.
> 각 분기의 ⚖ 표시는 현재 체감되는 트레이드오프의 발생 지점.

---

## 전체 흐름 (4단계)

```
[0] 전처리        좌표 미터화 → (저층 마스킹) → RDP 매크로 병합
[1] 형상 게이트    판상형(Case A)  vs  타워형(Case B)   ⚖①
[2] 벽면 분류      Case별 규칙 적용 (아래 트리)
[3] 후처리        매크로 라벨을 원본 선분에 전파
```

판정의 단위는 **매크로 벽면**(RDP로 병합된 벽)이고, 원본 선분은 소속 매크로의 라벨을 물려받는다.

---

## [0] 전처리

```
0-1  canvas px → 미터 변환 (metersPerPxFromGeoMapping, y축 반전)
0-2  forceConcrete? ──YES→ 건물 전체 concrete [lowrise_mask] ── 끝
     (저층 부속동 floors≤2 or height≤7m. 앱=꺼짐 / 검증뷰어=토글 ON)
0-3  RDP 매크로 병합 (ε = 1.2m)                              ⚖⑤
     · 1.2m 이내 요철은 하나의 벽면으로 흡수
     · 1m 미만 선분도 버리지 않고 병합에 포함 (둘레 보존)
```

---

## [1] 형상 게이트 — 어느 트리로 갈 것인가  ⚖①

```
최소면적 OBB 계산
├─ 채움비 fill ≥ 0.70  AND  종횡비 ≥ 2.0  →  Case A (판상형)
└─ 아니면                                →  Case B (타워/Y/L/비정형)
```

**⚖① 최대 트레이드오프 지점.** 두 트리는 규칙이 완전히 다르다(A는 축 기반, B는 수광+페어링).
게이트 경계(fill≈0.70, 종횡비≈2.0)에 걸친 건물은 어느 쪽으로 떨어지느냐에 따라 결과가 크게 달라진다.

---

## [2-A] Case A · 판상형 — 축 기반 (우선순위 순)

사전계산: OBB 장축의 두 법선 중 **150°(남남동)에 가까운 쪽 = 전면축**, 반대쪽 = 배면축.

```
매크로 벽면마다, 위에서부터 첫 매칭에서 종료:

A1  전면축·배면축 어느 쪽과도 35° 초과로 틀어짐?
     └─ YES → concrete [end_wall]          ← 마구리(단축) 격리
A2  길이 ≤ 3.5m?
     └─ YES → concrete [small_face]        ← 코어/설비 돌출     ⚖⑤
A3  전면축에 더 가까움?
     └─ YES → first  [front_axis]
A4  (나머지) → second [back_axis]           ← 배면은 무조건 second
```

특징: **페어링 없음, 경계밴드 없음.** 배면 장축은 조건 없이 second.
(판상형은 전면/배면이 구조적으로 명확하다는 가정 — 지금까지 이 가정에서 문제 보고 없음)

---

## [2-B] Case B · 타워/Y/L — 수광 + 페어링 (4패스)

사전계산: 매크로마다 중점(+28%/72% 지점)에서 **건물 내부로 레이**를 쏴
"마주보는 매크로"와 "관통 깊이"를 구해 둔다. sunScore = cos(방위각 − 150°).

### 1-pass · 즉시 확정 (우선순위 순)

```
B1  길이 ≤ 3.5m?
     └─ YES → concrete [small_face]                          ⚖⑤
B2  마구리(cap)인가?  (4조건 AND)
     · 양측 유의미 이웃(>3.5m)과 회전각 ≥ 45°
     · 양쪽 코너 모두 볼록(외향)
     · 길이 ≤ 17m (주동 단축폭 상한)
     · 내부 관통깊이 ≥ 1.5 × 자기 길이 (= 날개 장축 방향 관통)
     └─ YES → concrete [wing_cap]
B3  |sunScore| < 0.15?  (경계밴드: 방위각 60°/240° ±8.6°)
     └─ YES → 보류 → 1.5-pass로 [rel_pending]                ⚖④
B4  sunScore ≥ 0?  (방위각 60°~240° = 동~남~서)
     └─ YES → first [sun_front]                              ⚖②
B5  (나머지) → 보류 → 2-pass로 [pending]  (명확한 배면)
```

### 1.5-pass · 경계 상대판정 (v2.2 신설)  ⚖④

경계밴드에 걸린 벽은 절대 부호 대신 **마주보는 벽과 상대 비교**:

```
마주보는 매크로가 17m 이내에 있는가?
├─ NO  → 절대 규칙 폴백 (sunScore≥0이면 first, 아니면 pending)
├─ 상대가 이미 명확한 first → 나는 배면(pending)
├─ 내 sunScore > 상대 → first [rel_front]     ← 쌍 중 더 수광적인 쪽이 이김
└─ 내 sunScore < 상대 → 배면(pending)
```

목적: 60°/240° 경계에 걸친 단지에서 0.9° GIS 지터로 동일 유형 건물이
first↔concrete로 갈리던 나이프엣지 제거 (1908-4586).

### 2-pass · 배면-전면 페어링 (Y형 GT 반영)  ⚖③

```
배면(pending) 벽마다:
내부 레이 3점(28%/50%/72%) 중 하나라도
"17m 이내에서 first 벽"에 닿는가?
├─ YES → second  [paired_back]     ← 거실 뒤 주방/다용도실 창
└─ NO  → concrete [unpaired_back]  ← 마주볼 거실이 없는 벽
```

**⚖③** depthMax 17m = "세대 깊이" 가정. 단축폭 18m+ 건물은 페어링이 물리적으로
불가능해 배면이 전부 concrete (전수 기준 잔존 4동).

### 3-pass · 코어 샌드위치 흡수

```
first/second로 판정됐지만
길이 ≤ 8m AND 양측 유의미 이웃이 모두 concrete?
└─ YES → concrete [core_sandwich]   ← 콘크리트 사이 고립면 = 코어 전면일 확률
```

## 트레이드오프 지도 — "왜 조금씩 아쉬운가"

| # | 지점 | 증상 | 구조적 이유 |
|---|---|---|---|
| ⚖① | 형상 게이트 | 게이트 경계 건물이 A/B 어느 쪽이냐에 따라 결과 급변 | 두 트리의 규칙이 이질적 (A: 축, B: 수광) |
| ⚖② | sunAzimuth 150° 고정 | b6처럼 돌아앉은 건물은 "덜 남향인 쪽"이 second | **방위각이 유일한 first 신호** — 평면도·세대 배치 정보가 없음 |
| ⚖③ | depthMax 17m | 폭 18m+ 건물의 배면이 concrete | "second = 거실 맞은편"이라는 모델의 물리 한계 |
| ⚖④ | relBand 0.15 | 경계 밴드 안/밖에서 규칙이 바뀜 | 절대 문턱을 좁은 구간에서만 상대화한 절충 |
| ⚖⑤ | rdpEps/smallFace | 3.5m 이하 실제 창은 살릴 수 없음 | 코어·설비 돌출과 구분할 신호가 크기뿐 |

**공통 뿌리**: 이 트리는 입력이 **폴리곤 기하 + 방위각뿐**이다. first/second의 본질(거실이 어느 쪽인가)은
건축 정보인데, 그것을 기하로 근사하고 있어서 각 근사 지점마다 트레이드오프가 하나씩 생긴다.
전체 개선의 방향은 (a) 각 근사의 파라미터 튜닝, (b) 새 신호 추가(단지 일관성·평면 DB·층수),
(c) 확신도 출력(경계 케이스를 사용자 확인 대상으로 표시) 중에서 고르게 된다.
