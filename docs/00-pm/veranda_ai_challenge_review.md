## 2. 발견된 구조적 결함 (챌린지 포인트)

### 2.1 [치명] 판상형 게이트 `R ≥ 0.60`은 "종횡비 4:1 이상"과 등가

순수 직사각형(L×W)에서 주축 집중도는 R = (L−W)/(L+W). 따라서 **R ≥ 0.6 ⇔ L ≥ 4W**.
`AND aspect ≥ 2.0` 조건과 결합하면 사실상 4:1 초과 초장형 주동만 판상형으로 인정된다.
전형적 판상형(40m×12m, 3.3:1)조차 R=0.538로 탈락 → Case B(타워 로직)로 유입.

* 실측: OBB 기준 명백한 판상형(채움비 ≥0.75, 종횡비 ≥2) 아파트 **731동 중 59동(8%)만 isSlab=True**.
* Gemini가 인용한 타워 단지(`m-RAPA-2303-0883`)의 "R=0.05~0.14라 100% 정확 판별"은 사실이지만, **타워를 타워로 판별한 것만 보여주고 판상형을 판상형으로 판별하지 못하는 것은 보여주지 않은 선택적 검증**이다.

### 2.2 [치명] 좌표계 왜곡 버그 2건 (각각 다른 파일에서)

* `generate_viewer.py`: 종횡비(aspect)를 **스케일 보정 없는 raw lon/lat 좌표를 회전**시켜 계산. 위도 1도(111km)와 경도 1도(88.8km)의 비등방성 때문에 회전 각도에 따라 종횡비가 왜곡됨. 실측 평균 오차 0.47, 최대 **18.6**. 예: 신반포(`m-RAPA-2411-3075` b12, 10층)는 실제 종횡비 8.46인데 1.47로 계산되어 판상형 탈락 → 양단 마구리가 first/second로 출력.
* `App.tsx toCanvas()`: lon/lat을 캔버스 폭/높이에 **각각 독립 정규화**하므로 캔버스 자체가 단지마다 다른 비율로 늘어남 → TS `verandaAi.ts`가 계산하는 방위각·종횡비·법선이 전부 왜곡. 검증 뷰어(python)와 실제 앱(TS)이 서로 다른 결과를 내는 원인이기도 함.

### 2.3 [중대] 문서와 구현의 괴리

`advanced_veranda_ai_setting.md`가 약속한 핵심 기능 중 미구현:

* §4.2 **Collinear 선분 병합(Macro-Edge Merge)** — 코드 어디에도 없음. 증상 ②의 직접 원인.
* §2 "국소 윙(Wing)별 수광 지수 평가" — 실제 구현은 **전역 SunScore 부호 하드컷 1줄**. 날개 개념 없음.
* §6 테스트 매트릭스 "✅ PASS 검증 완료" — 이상적 직사각형/Y형 5건뿐, 실데이터 검증 아님. 판상형 게이트를 통과 못 하는 Test 1~4 형상(종횡비 명시 없음)이 실데이터에선 대부분 Case B로 빠진다.

### 2.4 [중] 기타

* **1m 미만 선분 silent drop**: 콘크리트 분류가 아니라 **미분류 누락**. Gemini 분석문 중 "콘크리트벽: 1m 미만 계단실/코어 단차 9.9m(5.2%)"는 사실과 다름 — 1m 미만은 결과에서 사라지며, 해당 동(`b6`) 실측 재계산은 콘크리트 6.1m(3.3%)로 인용 수치(191.3m/86.8/94.6/9.9)와 불일치.
* **TS/Python 상수 불일치**: notch 문턱 TS `(max>30 && l<8)` px vs Python `(max>25 && l<7)` m — 단위조차 다름(px vs 미터).
* **median 기반 notch 문턱의 취약성**: 버텍스 밀도가 높은 단지(평균 선분 2.2m)에서는 median이 작아져 마구리(10~14m)가 절대 걸러지지 않음. Gemini의 "35° 필터를 안 쓴 덕분에 날개가 살았다"는 방어는 절반만 타당 — **병합을 먼저 했으면 둘 다 가능**했다.
* 저층 부속동(상가/경비실, floors≤2) **9,303동 전부**에 베란다 생성 (Gemini도 스스로 챌린지로 인정한 부분).

## 3. Y형 Ground Truth 반영 (사용자 제공 이미지)

사용자 확인 GT: Y형 주동에서 **1차 = 날개 바깥 수광면(남향 계열)**, **2차 = V자 요입부 안쪽 면만**, 날개 바깥 배면과 마구리는 일반 벽.

이를 일반화한 규칙이 v2의 **배면-전면 페어링**:

> 배면(수광 아님) 벽은 내부로 레이를 쐈을 때 **세대 깊이(≤17m) 이내에서 1차 베란다 벽과 마주볼 때만** 2차 베란다. 아니면 콘크리트.

* V자 요입부 안쪽 면 → 같은 날개의 전면(1차)과 10~14m 깊이로 마주봄 → **2차** ✓
* 날개 바깥 배면 → 마주보는 면이 요입부(비-1차)이거나 관통 깊이가 큼 → **콘크리트** ✓
* 판상형 배면 → 전면과 슬래브 깊이로 마주봄 → 2차 (기존 동작 유지) ✓

## 4. v2 알고리즘 요약

```
[lon/lat 또는 canvas px] → 미터 복원 (metersPerPxFromGeoMapping: 캔버스 비등방 왜곡 보정)
  → ① RDP 매크로엣지 병합 (ε=1.2m, 요철 흡수·둘레 보존, <1m drop 제거)
  → ② 최소면적 OBB 게이트: fill ≥ 0.70 AND aspect ≥ 2.0 → 판상형
  ├─ [Case A 판상형] OBB 장축 법선 기준 first/second, 단축(>35°) 마구리 + ≤3.5m 미세면 = 콘크리트
  └─ [Case B 타워형] 
       1-pass: ≤3.5m 미세면 / cap(양측 볼록 ≥45° 코너 + ≤17m + 관통깊이 ≥1.5×길이) = 콘크리트,
               SunScore ≥ +0.10 = first (히스테리시스 밴드)
       2-pass: 배면-전면 페어링 (내부 레이 ≤17m에서 first와 마주보면 second, 아니면 콘크리트)
       3-pass: 콘크리트 사이 고립 ≤8m 면(코어 전면) 흡수
  → (옵션) floors_above ≤ 2 저층 부속동 전체 콘크리트 마스킹
```

주요 파라미터는 전부 `VerandaAiOptions`로 노출 (기본값: rdpEps 1.2m, smallFace 3.5m, capLenMax 17m, capDepthRatio 1.5, sunBand 0.0, depthMax 17m, endWallAng 35°, slabFill 0.70, slabAspect 2.0, sunAzimuth 150°).

### 4.1 v2.1 셀프챌린지 수정 (rapaKey 2206-3699 사례)

사용자 피드백: 같은 단지의 V자형 동들 사이에서 (a) 왼쪽 V 날개에 베란다가 전혀 없거나, (b) 오른쪽 V 안쪽 2차가 동마다 다르게 누락됨.

원인 2건을 확인하고 수정:

1. **히스테리시스 밴드의 연쇄 실패**: 초기 v2는 first 문턱을 sunScore ≥ 0.10(약 60~234°)으로 잡았는데, 이 단지 주동들의 남서 외측면이 az231°(score 0.156, 통과) vs az235°(score 0.087, 탈락)로 **4° 차이로 동마다 갈렸다**. first가 탈락한 날개는 배면 페어링까지 연쇄 실패해 V 안쪽 2차가 전멸. → **문턱을 스펙(60~240° = score ≥ 0)으로 환원**. flip 방지는 밴드가 아니라 매크로 병합이 담당 (전수 flip 20건, v1 23건 대비 소폭 개선 유지).
2. **중점 1점 레이의 취약성**: 배면 페어링 레이를 매크로 중점에서 1발만 쏘면 요철/코너에 걸려 같은 형상에서도 결과가 갈림. → **3점 샘플(28%/50%/72%)로 보강**, 하나라도 first에 닿으면 second.

수정 후 2206-3699 전 동에서 왼쪽 날개 외측면 first 복원 + 양쪽 V 안쪽 2차 페어링 정상화 확인 (TS-Python 파리티 107/107 재통과).

### 4.2 v2.2 경계 상대판정 (rapaKey 1908-4586 사례)

사용자 발견: 같은 유형 건물인데 왼쪽 장벽이 동마다 first / second / concrete로 제각각.

원인: 이 단지는 장벽 법선이 az 239~241° — **수광 스펙 경계(60°/240°, sunScore=0)에 정확히 걸친 배치**.
b1(239.59°, sun +0.0072)은 first, b2(240.47°, sun −0.0083)는 배면 → 반대면(58.87°)도 배면이라
first 부재로 페어링 연쇄 실패 → 양쪽 장벽 모두 concrete. **건물 간 0.9° GIS 지터가 결과를 가름.**
전수 스캔: 경계 ±2°에 15m+ 장벽이 걸린 건물 115동(3.4%)/32개 단지 — 특이 케이스가 아님.

수정(`relBand`, 기본 0.15): |sunScore| < 0.15인 장벽은 절대 부호 대신 **마주보는 장벽과 sunScore를
비교해 더 수광적인 쪽을 first**로 판정(rel_front). 마주볼 상대가 없으면 기존 절대 규칙으로 폴백.
검증: 1908-4586 b2/b3/b5 장벽 first 복원(b1과 일관), 2206-3699·0883 **완전 무변화**(회귀 0),
전수 3,430동 중 129동(3.8%)만 변화(콘크리트 −1.3km → 2차 +1.2km), 경계 장벽 사망 잔존 4동은
단축폭 18~40m > depthMax(17m)인 별도 한계. TS-Python 파리티 136/136.

## 4.3 perp_cap (3.5-pass, 2026-08-16 적용) — Y형 "몸통부 측면=콘크리트" GT 반영

사용자 제공 정밀 GT(Y+셔츠형 건물, 주석 이미지 2장): "날개부분의 측면은 베란다"(기존 로직과 일치) /
"아랫부분(몸통)에서 아랫면만 베란다, 측면은 콘크리트"(기존 로직과 불일치 — 몸통 측면의 짧은 수직
세그먼트가 first로 오분류되고 있었음).

원인: 몸통(슬래브 스트립)의 세로 마구리(짧은 수직 세그먼트)는 뒤에 세대 깊이가 없는데도, 기존
cap 판정(`wing_cap`)이 "양측 볼록 코너" 조건만 보고 "한쪽만 볼록 + 다른 한쪽은 몸통 장벽과 직교"인
이 케이스를 못 잡음 → sunScore 조건만으로 first 처리됨.

수정(`perpCap`, 기본 true): 길이 `capLenMax`(17m) 이하의 first 벽이, 자신보다 1.3배 이상 긴 first
벽과 수직(75~105°)·볼록 코너로 인접하고, 내부 관통 깊이가 `depthMax`(17m)를 넘으면(=뒤에 세대가
없으면) concrete로 재분류. 날개 측면은 관통 깊이가 날개폭(≤depthMax)이라 이 규칙에 걸리지 않음.

검증:
- GT 셔츠형 몸통측면 5/5 적중 (0883 b1/b2/b3/b11/b12, az63~80°, ~11m → concrete)
- 기존 확정 GT(Y형 날개 측면·V요입부·팁) **완전 무변화**
- 전수 3,430동(아파트급) 중 Case B 1,010동(29.5%) 변화, first −6.5km → concrete +6.5km, second 무변화
- 무작위 6동 육안 검증: 전부 동일 구조 클래스(직선 스트립 세로 마구리), 이질적 오탐 없음
- **판상형(Case A)은 relBand·perpCap 둘 다 코드 경로 밖 — 항상 무변화 (수학적으로 보장, 전수 확인)**
- TS ↔ Python 파리티 30/30 (판상형 1 + V/T/Y 4 + 무작위 25)

3-way 비교(HEAD=state1 vs relBand만=state2 vs relBand+perpCap=state3)로 판상형/V/T/Y 4개 실제 사례를
렌더링해 사용자 확인 후 **state3(현재 상태)로 최종 채택**.

## 6. 적용 내역 및 사용법

1. **`src/lib/verandaAi.ts`** — v2로 교체 완료 (기존 export 시그니처 호환: `classifyBuildingWalls`, `generateAutoVerandas`, `isPointInPolygon` 유지, `metersPerPxFromGeoMapping`/`isLowRise` 추가). 각 벽에 `reason` 필드(판정 사유) 포함.
2. **`src/App.tsx`** — `handleAiAutoVerandas`에서 `geoMapping` 기반 미터 환산 옵션을 전달하도록 1줄 패치 (캔버스 왜곡 보정의 핵심).
3. **`public/veranda_ai_viewer_v2.html`** — 신구 로직 좌우 비교 뷰어 신규. 데이터를 임베드하지 않고 `temps/*.json`을 fetch하므로 **재생성 불필요**(기존 35MB 뷰어와 달리 로직 수정 시 파일 하나만 교체). vite dev 서버에서 `/veranda_ai_viewer_v2.html`로 접근. 호버 시 벽별 판정 사유 툴팁, 저층 마스킹 토글 제공.
4. 저층 부속동 마스킹은 **앱에서는 기본 미적용**(buildingsMeta 미전달), 뷰어에서는 토글(기본 ON) — RF 설계 정책 확정 후 `generateAutoVerandas` 4번째 인자로 `moira.buildings`의 층수를 넘기면 됨.

## 7. 남은 의사결정 (열린 항목)

* **최적 수광 방위각 150° 고정**: 단지 배치가 극단적 서향/동향인 경우의 정책(현재는 히스테리시스+페어링으로 완화). 필요시 단지별 주동 평균 방위로 적응화 가능.
* **정방형 타워(폭 >17m)의 2차 베란다**: 페어링 깊이 초과로 2차가 나오지 않음. 실제 GT 확보 시 `depthMax` 조정.
* **저층 부속동 마스킹 기본값**: floors 데이터 신뢰도 확인 후 앱 기본 ON 여부 결정.
* 파라미터 미세 튜닝은 뷰어 v2로 단지별 확인하며 `VerandaAiOptions`로 조정.
